# 議事録作成（Minutes）

**とーるさんは材料を投げるだけ。あとは全部こっちでやる。**
コマンドを打たせない。ファイルパスを探させない。体裁を考えさせない。

## 受け取れるもの（何でもいい）

| 渡されたもの | どうする |
|---|---|
| 打ち合わせメモ・走り書き | そのまま整える |
| 文字起こしテキスト | 誤変換を直しながら整える |
| 音声ファイル | 文字起こしできる環境なら起こす。無理なら正直に言って文字起こしを頼む |
| 議事録の様式の写真 | 先に書式プロファイルを作る（下の「様式の写真が来たとき」） |
| 第4表の写真・「第4表で」の指定 | 第4表モードで作る（下の「第4表を頼まれたとき」） |
| 何も付いていない | 「メモか文字起こしを貼って」と一言だけ |

## 進め方（この順で、全部自分でやる）

### 1. 足りないものを聞く（勝手に埋めない）

材料を読んで、下が揃っているか確認する。

| 項目 | 無いときどうするか |
|---|---|
| 会議名 | **聞く**（議事録の見出しになるので推測で埋めない） |
| 日時 | 材料にあればそれ。無ければ今日の日付を仮置きして、報告で「今日にしたけど合ってる？」と添える |
| 出席者 | **聞く**。ただし「分かる範囲で」と言われたら「（記載なし）」で進める |
| ToDo の担当・期限 | 材料から読めなければ**聞く**。決まっていないなら「次回までに決める」を ToDo にする |
| 事業所の様式 | 標準の体裁で作る。事業所の様式に合わせたいなら様式の写真をもらう |

**聞き方のルール**
- 足りないものは**まとめて1回で聞く**。1つずつ往復しない
- 「分からない」「任せる」と返ってきたら、そこは `（記載なし）` か `［要確認］` にして先に進む。聞き直さない
- **聞かずに創作するのが一番まずい。** 材料に無い決定事項・出席者・日付を足さない

### 2. 議事録に整える

- **材料に無いことは書かない。** 聞き取れない・読み取れない箇所は `［要確認］` と明示する
- 利用者名は `A様` `B様` に仮名化する。材料に実名があっても議事録に残さない
- 雑談・脱線は落とす。ただし決定に影響した発言は残す
- 決定事項は「決まったこと」だけ。検討中のものは要旨側に残す

標準の体裁（プロファイル指定が無いとき）:

```
議 事 録
  会議情報（会議名／日時／場所／出席者／欠席者／記録者）
  1. 議題
  2. 議論の要旨
  3. 決定事項（表：No／決定事項／補足・根拠）
  4. ToDo（表：No／内容／担当／期限）
  5. 次回予定
  6. ［要確認］一覧
```

事業所の書式プロファイルが渡されている／`company/secretary/minutes/formats/` にある場合は、
**項目名・並び・表の列をプロファイルのとおりにする**（言い換えない）。
そのうえで、プロファイルに無くても ToDo の「担当」「期限」列と `［要確認］一覧` は足す。

### 3. Word にする

docx スキルで .docx を作る。**とーるさんに `node` を打たせない。**
空のテンプレートが必要なだけなら、自分で
`node templates/build-meeting-minutes-template.js <プロファイル.json>` を走らせる。

### 4. 配布前チェックを走らせる（省略しない）

```bash
python3 templates/check-minutes.py <作った.docx> --preview /tmp/minutes-preview
```

依存パッケージは要らない。出力の読み方:

- **「配布前に直すところ」が出たら、自分で直して作り直す。** とーるさんに直させない
  - ただし `［要確認］` の中身と、仮名化されていない氏名は**材料を見ないと直せない**ので、
    直さずに残して報告で聞く
- 「見ておいた方がいいところ」は報告に含める
- 判定が「配布できる」になるまで繰り返す

### 5. 目視で確認する

`--preview` で出た画像を**自分の目で見る**（Read で開く）。見るところ:

- 表が右にはみ出していないか
- 変なところで改ページしていないか
- フォントが当たっているか（豆腐 `□□□` になっていないか）
- 見出しと本文の区別がついているか

崩れていたら直して作り直す。
**画像が作れない環境だった場合は、その旨を報告に書く**（「レイアウトは未確認、Word で開いて確認して」）。
作れていないのに「確認した」と書かない。

### 6. 保存して報告する

保存先:
- `company/secretary/minutes/YYYY-MM-DD_<タイトル>.docx`
- 同日同タイトルがあれば連番（`_2` など）
- Markdown 版は作らなくてよい（配布するのは Word）

報告の形（これだけ。長く書かない）:

```
議事録できたよ → <パス>

配布前チェック: 通った ／ 気になる点 N 件
レイアウト: 見た（崩れなし） ／ 未確認（Wordで見て）

〔聞きたいこと・確認したいことがあれば1〜3個だけ〕
```

## 第4表（サービス担当者会議の要点）を頼まれたとき

ケアマネジャーが担当者会議のあとに必ず書く法定様式。
`templates/profiles/careplan-4.json` を使う。**ここだけ普段と作法が違うので注意。**

### 普段と違うところ

| | 普段の議事録 | 第4表 |
|---|---|---|
| 欄を足すか | 担当・期限列、［要確認］一覧、配布前チェック欄を足す | **足さない。**法定様式なので改変しない |
| 未確認の印 | `［要確認］` | `［AI提案・要確認］`（AIが推測した箇所） |
| 立場 | 議事録 | **下書き。**ケアマネジャーの確認・修正が前提 |

### 守ること

1. **AI が推測した箇所すべてに `［AI提案・要確認］` を付ける。**
   材料に書かれていた事実には付けない（ここを混ぜると意味がなくなる）
2. **氏名を補わない。** 会議出席者の「氏名」欄は空欄のまま残す。
   所属（職種）は材料から埋めてよい
3. **冒頭と末尾に「下書きである」ことを書く。**
   末尾は「本下書きは介護支援専門員の確認・修正を前提としています」
   （タグを消したら、この2行も消す前提で書く）
4. 利用者名は `A様` に仮名化する
5. 「検討内容」は記載要領どおり、サービス内容だけでなく
   **提供方法・留意点・頻度・時間数・担当者**まで具体的に。第三者が読んで分かるように
6. 会議に**出席できなかった担当者**がいれば、所属（職種）・氏名と**欠席の理由**も書く
7. 保留になったことは「結論」に入れず「残された課題」に回す
8. 「残された課題」には**次回の開催時期**を必ず入れる

### 配布前チェックの読み方が変わる

第4表の下書きは、`［AI提案・要確認］` が残っているので
**チェックは必ず「まだ出せない」と出る。それが正しい。**
ケアマネジャーが確認してタグを消すと通るようになる。
「チェックが通らないから」とタグを勝手に消さない。

### 様式が手元のものと違ったら

第4表の様式は自治体や介護ソフトで細部が違う。
**とーるさんの手元の第4表の写真をもらって、それを正にする。**
プロファイルの項目名を写真に合わせて直す。

## 様式の写真が来たとき（初回だけ）

1. 写真から**項目名・並び・表の列**を読み取る
2. `templates/profiles/default.json` と同じ構造の JSON にする
3. **写真に書かれている記入内容は転記しない。** 項目の枠組みだけ写す
   （プロファイルに要配慮個人情報が入ると、以後ずっと持ち回ることになる）
4. `improvements` は 3 つ全部 true
5. `company/secretary/minutes/formats/<事業所名>.json` に保存する
   - **dev-notes は公開リポジトリなので `templates/profiles/` には置かない**
6. 読み取れなかった項目は `〔要確認〕` を placeholder に入れて、最後に何が読めなかったか報告する
7. そのまま議事録も作れるなら続けて作る

## コミュニケーション

- フランクに。結果を先に出して、保存報告は最後に短く
- **とーるさんに作業をお願いしない。** コマンド実行・パス探し・体裁直しは全部こっちでやる
- 例外は2つだけ：**材料が足りないとき**と、**レイアウト画像が作れなかったとき**
- 迷ったら「創作しない・聞く」を選ぶ
